Agentensysteme & KI-Integration

Agentensystem/
Drei Protokolle verbinden hier unterschiedliche Dinge — und genau diese Unterscheidung ist der Kern des Themas. MCP verbindet ein Sprachmodell mit Werkzeugen und Daten (die „vertikale" Kante) — so bekommt Claude Desktop unten Zugriff auf die MariaDB. A2A verbindet zwei eigenständige Agenten miteinander (die „horizontale" Kante) — der Orchestrator delegiert Aufgaben an den DB- und Report-Agenten. LAP verbindet einen Agenten mit einem physischen Gerät — hier ein Diagnosegerät, das der Wartungs-Agent erst nach einer expliziten Sicherheitsbestätigung ansteuern darf. Der Agent Harness schließlich ist die Schleife, die aus einem rohen Sprachmodell überhaupt erst etwas macht, das Werkzeuge selbstständig benutzen kann — genau das lässt sich oben im Chat-Tab „Agenten-Konsole" gegen die echten A2A-Agenten ausprobieren.

Architektur

Der Orchestrator-Agent überwacht die Datenkrake und greift bei Bedarf per LAP auf sein eigenes Zusatzgerät zu — nie auf eine Produktionssteuerung. Das YOLO-System ist im Schema als "geplant" markiert, siehe README zur aktuellen Datenlage.

Datenerhebung

ArduinoUnoQ/, Raspberry/nodered/, UAExpertExport/
In diesem Schritt entstehen die Rohdaten: Akustikwerte vom Arduino UNO Q, später optische Signale (YOLO-System) sowie SPS-Tags aus der Modellanlage via OPC-UA. Diese Daten werden im Takt erfasst, über MQTT/Node-RED zusammengeführt und als Grundlage für spätere Auswertung und Modelle abgelegt.

Machine Learning

ArduinoUnoQ/, Agentensystem/anomalie_poller/
Hier wird aus den erhobenen Akustikdaten ein Anomalie-Detektor abgeleitet: Muster aus dem Spektrum werden bewertet und als Abweichungen markiert. Genau diese Erkennung ist die Brücke zum operativen Teil: der anomalie_poller schreibt erkannte Fälle und übergibt sie an die Agentenkette für Reaktion, Wartung und Reporting.

Vergleich von ML-Verfahren

📈 Lineare Regression
Vorteile: gut interpretierbar, schnell trainiert. Nachteile: nur lineare Zusammenhänge, empfindlich bei Ausreißern.
📉 Logistische Regression
Vorteile: robuste Baseline für Klassifikation, Wahrscheinlichkeiten. Nachteile: lineare Entscheidungsgrenze, ggf. Feature-Engineering nötig.
🌳 Entscheidungsbaum
Vorteile: leicht erklärbar, nichtlineare Regeln möglich. Nachteile: overfitting-anfällig, instabil bei kleinen Datenänderungen.
📬 Naiver Bayes
Vorteile: sehr schnell, wenig Datenbedarf. Nachteile: Unabhängigkeitsannahme oft zu stark, bei korrelierten Features schwächer.
📍 kNN
Vorteile: kein explizites Training, flexibel. Nachteile: langsam bei vielen Daten, skalenempfindlich und abhängig von k/Distanzmaß.
📦 Daten für lokale Analyse
Die Messdaten werden aus der MariaDB exportiert, damit sie lokal in Orange3 oder Jupyter weiterverarbeitet werden können.
CSV: Spektrum ↗ CSV: PLC-Telemetrie ↗ CSV: alle Daten ↗

Wie arbeitet anomalie_poller/poller.py?

Diese Uebergangslogik verbindet die Akustik-Erkennung mit dem Agentensystem, bis ein echter Echtzeit-Inferenz-Output vom Arduino vorliegt.

Zweck

Uebergangsloesung

Der Poller schliesst die Luecke, solange die Anomalie-Erkennung noch nicht direkt vom Arduino als Event publiziert wird.

Quelle waehlen

Per Umgebungsvariable ANOMALIE_QUELLE wird zwischen influx (Standard) und mariadb umgeschaltet.
Ablauf im Zyklus

1. Periodisches Pruefen

Alle 15 Sekunden wird pruefzyklus() aufgerufen und eine statistische Pruefung gestartet.

2. Anomalie-Check

Aufruf von pruefe_akustik_anomalie_influx() oder pruefe_akustik_anomalie() je nach Quelle.

3. Duplikate vermeiden

Mit anomalie_bereits_erfasst(bezug_id) werden Mehrfacheintraege fuer dieselbe Messung verhindert.

4. Persistenz fuer Agenten

Bei Treffer schreibt insert_anomalie(...) einen Datensatz in audio_anomalien als Trigger fuer Orchestrator/Wartung/Report.
Didaktischer Uebergang

Heute im Unterricht

ML-Modelle vergleichen (Orange3/Jupyter), daraus einen Detektor ableiten, dann den Weg in die Agentenkette nachvollziehen.

Naechster Ausbauschritt

Wenn der Arduino echte Inferenz-Events liefert, kann diese Poller-Datei durch einen MQTT-Listener ersetzt werden.

Datenhaltung und -analyse

Raspberry/mariadb/, Raspberry/historian/, DataLake/
Zwei Datenbanken für dieselben Messwerte — das wirkt zunächst seltsam, ist aber ein anerkanntes Prinzip: Polyglot Persistence. Die MariaDB bleibt die einzige vollständige Quelle (inklusive des kompletten Spektrums, das fürs Training gebraucht wird), der Operational Historian daneben ist auf schnelle Zeitreihen-Abfragen optimiert. Für Analyse und Aufbereitung kommen zusätzlich Grafana sowie der Data-Lake-Stack (MinIO, Nessie/Spark) zum Einsatz.

Kommunikation & Industrie 4.0

Raspberry/mosquitto/, Raspberry/nodered/
MQTT und OPC-UA lösen unterschiedliche Probleme. MQTT ist ein schlankes Publish/Subscribe-Protokoll, mit dem der Arduino seine Messwerte „hinausruft", ohne zu wissen, wer zuhört. OPC-UA ist der etablierte Industriestandard, mit dem Maschinen wie eine S7-1500 ihre Daten strukturiert bereitstellen. Node-RED übersetzt zwischen beiden Welten, ganz ohne eigenen Code — die SPS-Werte landen anschließend auf dem MQTT-Topic-Namensraum plc/<station>/<tag>.

Gemeinsame OPC-UA-Grundstruktur je Station

1. Geräte-Metadaten

  • DeviceManual, DeviceRevision, EngineeringRevision
  • Manufacturer, Model, SerialNumber, SoftwareRevision
  • OperatingMode (typisch: 8 = Run)

2. Inputs

  • Sensoren, Bedienbits, Handshake-Eingänge
  • Typisch viele Boolean-Signale, einige UInt16/Int16/UInt32

3. Outputs

  • Aktoren, Stellbits, Handshake-Ausgänge
  • Typisch viele Boolean-Signale

4. DataBlocksGlobal/dbMESStation

  • MES-relevante Kennzahlen und Strukturfelder
  • z. B. Arbeitsgang, Auftragsnummern, Fehler, Füllstände, Mengen, Zustand

5. DataBlocksGlobal/dbOPCLeitstand

  • Auftrags- und Statusaustausch mit Leitstand
  • z. B. uvlaVonLeitstandAuftrag, uzlsZuLeitstandStatus

Stationsspezifische Hinweise

  • Zentrale Sammel-/Steuerinstanz, 1000 Datensätze
  • viele stationsübergreifende Handshake-Signale

Datenmodell für MQTT

Empfohlenes Topic-Schema: fabrik/linie1/<station>/heartbeat · .../process_io · .../mes · .../order_link · .../status_link
Beispielstationen: leitstand, palettenlager1, rohlager, abfuellen, qualitaet, handling, presse, palettenlager2, transfer_roboter, transfer_hochregal

{ "ts": "2026-08-05T10:00:00.000Z", "station": "abfuellen", "group": "process_io", "quality": "Good", "values": { "+AM-BG11_FuellstandMag1": true, "+AN-BG1_WaageGS": true, "sWartet": true } }

Hinweise: ts immer in UTC (ISO-8601) · quality aus dem OPC-UA-StatusCode mitgeben · bei Arrays/Strukturen flache Key-Namen mit Pfad verwenden.

Sampling- und Logging-Strategie

1. Zyklische Erfassung

  • Prozessbits und MES-Werte alle 500–1000 ms

2. Event-basierte Ergänzung

  • zusätzlich bei Flankenwechsel von Status_Error, sStillstand, sInReset, Schlüsselsensoren (Stopper, Hub, Vakuum)

3. Datenqualität

  • nur quality = Good für Modelltraining
  • ungültige/fehlende Werte als eigene Klasse markieren, nicht still löschen

Raspberry/compose/, ArduinoUnoQ/
